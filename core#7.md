# Календарный план и критерии приёмки (Core #7) 

## 1. Введение
Данный документ определяет этапы реализации проекта «vbudushee», временные рамки ключевых вех (milestones) и конкретные требования, при выполнении которых функционал считается принятым. План составлен с учетом текущего состояния кодовой базы (реализовано ядро Django, модели данных и базовые задачи Celery).

---

## 2. Календарный план (Этапы разработки)

Учитывая текущую готовность Backend-части, проект разбивается на 4 ключевых этапа.

| Этап | Наименование | Срок (недели) | Ключевой результат (Deliverable) |
| :--- | :--- | :--- | :--- |
| **Этап 1** | **Стабилизация ядра и RAG-конвейера** | 1-2 | Стабильная индексация PDF/Docx, поиск по PGVector, базовый ответ от OpenAI/Anthropic. |
| **Этап 2** | **Frontend и виджет чата** | 2-3 | Полноценный MPA-интерфейс для управления проектами и JS-виджет для встройки на сторонние сайты. |
| **Этап 3** | **Интеграция локальных моделей и TUS** | 2 | Поддержка vLLM/Ollama, стабильная загрузка больших файлов через протокол TUS. |
| **Этап 4** | **Биллинг, безопасности и запуск** | 2 | Ограничение лимитов по подпискам, аудит безопасности, деплой в продакшн-окружение. |

**Итого ориентировочный срок реализации: 8-9 недель.**

---

## 3. Критерии приёмки (Acceptance Criteria)

### 3.1. Управление проектами и источниками
- [ ] Пользователь может создать проект, задать ему имя и системный промпт.
- [ ] Источники (файлы, сайты) успешно добавляются и отображаются в списке.
- [ ] Статус индексации корректно обновляется в реальном времени (через WebSocket или опрос API).
- [ ] Удаление источника приводит к удалению всех связанных чанков из векторной БД.

### 3.2. Система индексации (RAG Pipeline)
- [ ] Тексты из PDF и Docx извлекаются без потери значимой структуры.
- [ ] Краулер корректно обходит заданные URL и не уходит в бесконечные циклы (соблюдение `robots.txt`).
- [ ] Эмбеддинги генерируются и сохраняются в PGVector с корректным вектором размерности (например, 1024).
- [ ] Реализован механизм дельта-обновлений (переиндексируются только измененные файлы по хешу).

### 3.3. Чат и взаимодействие с LLM
- [ ] Ответы приходят через WebSocket в потоковом режиме (streaming).
- [ ] Система предоставляет ссылки на источники (цитирование) в формате Markdown.
- [ ] Переключение между моделями (OpenAI, Anthropic, Local) происходит без изменения логики фронтенда.
- [ ] История чата сохраняется в БД и доступна после перезагрузки страницы.

### 3.4. Виджет и внешняя интеграция
- [ ] Виджет инициализируется на стороннем домене через вставку JS-кода.
- [ ] Стили виджета не конфликтуют с глобальными стилями сайта-хоста (использование Shadow DOM или изолированных префиксов).
- [ ] WebSocket-соединение защищено временным токеном, предотвращающим несанкционированное использование API.

### 3.5. Производительность и Наблюдаемость
- [ ] Время генерации первого токена (TTFT) не превышает 2 секунд (при доступности API LLM).
- [ ] Система выдерживает до 50 одновременных WebSocket-сессий на один инстанс без деградации.
- [ ] Ошибки логируются в Sentry, метрики доступны в Grafana.

---

## 4. Порядок приемки

1. **Демонстрация функционала**: Разработчик демонстрирует выполнение сценариев согласно критериям выше на тестовом стенде.
2. **Проверка кода (Code Review)**: Соответствие стандартам проекта, отсутствие хардкода ключей, наличие документации.
3. **Нагрузочное тестирование**: Проверка стабильности работы под нагрузкой (индексация 100+ документов одновременно).
4. **Подписание акта**: После устранения замечаний этапа подписывается промежуточный или итоговый акт приемки.

---

## 5. Риски и допущения
- **Доступность API**: Сроки могут сдвигаться при нестабильной работе зарубежных провайдеров LLM.
- **Инфраструктура**: Предполагается наличие GPU-мощностей для запуска локальных моделей на 3-м этапе.
