# План: Корпусная частотность шинглов

## Как хранить частотность шинглов по корпусу

1. **Где считать:**
  - При каждом обновлении/добавлении документа считать шинглы для всего корпуса (или поддерживать инкрементально).
  - Использовать отдельную таблицу или файл (например, `shingle_freq.json` или таблица `shingle_frequency` в БД).

2. **Что хранить:**
  - Для каждого уникального шингла:
    - Сам шингл (строка)
    - Количество документов, где он встречается (`doc_count`)
    - Общее количество вхождений по корпусу (`total_count`)
    - Последний апдейт (timestamp)

3. **Как использовать:**
  - При обработке нового документа:
    - Обновлять счетчики для каждого шингла
    - Сохранять в meta документа snapshot частотности его шинглов (например, `meta['shingle_stats']`)
  - Для аудита и визуализации — показывать частотность каждого удалённого шингла

4. **Техническая реализация:**
  - Для MVP: отдельный JSON-файл с маппингом {shingle: {doc_count, total_count}}
  - Для production: отдельная таблица в Postgres с индексом по шинглу

5. **Пример структуры (JSON):**
```json
{
  "и вот однажды в лесу": {"doc_count": 12, "total_count": 37, "last_update": "2026-04-29T12:00:00Z"},
  "все дети собрались": {"doc_count": 5, "total_count": 8, "last_update": "2026-04-29T12:00:00Z"}
}
```

---

**Резюме:**
- Частотность шинглов по корпусу хранится централизованно (файл или таблица).
- В meta документа можно сохранять только snapshot для его удалённых шинглов.
- Для аудита и анализа всегда можно получить глобальную статистику по любому шинглу.
# План: Корректное хранение и использование шинглов для удаления навигации/boilerplate

## 1. Явное хранение удалённых шинглов
- Для каждого документа сохранять список удалённых шинглов (и их позиции/окна) в поле `meta['removed_shingles_raw']` (JSON, список строк или структур).
- Визуализация: хранить не только HTML для UI, но и исходные данные для аудита и отладки.

## 2. Хранение статистики по шинглам
- В `meta['shingle_stats']` сохранять:
  - Количество удалённых шинглов
  - Долю удалённого текста
  - Частотность шинглов по корпусу

## 3. Улучшение extraction pipeline
- После удаления boilerplate/навигации:
  - Сохранять результат удаления в отдельное поле (например, `meta['boilerplate_blocks']`)
  - Сохранять результат удаления шинглов в `meta['removed_shingles_raw']`
  - Сохранять итоговый очищенный текст и его статистику

## 4. API и тесты
- Добавить API/скрипт для аудита: показать, что реально хранится в meta по каждому документу
- Покрыть тестами: при каждом обновлении документа проверять, что шинглы реально сохраняются и доступны

## 5. Миграция и обратная совместимость
- Для старых документов: отдельный скрипт для пересчёта и сохранения шинглов в meta
- Для новых: pipeline всегда пишет нужные поля

## 6. Документация и визуализация
- Описать структуру meta и формат хранения шинглов
- В UI добавить отображение не только summary, но и "raw" удалённых шинглов для эксперта

---

**Цель:**
- Любой документ после обработки содержит в meta:
  - исходные удалённые шинглы (raw)
  - визуализацию для UI
  - статистику по удалению
- Любой разработчик/эксперт может проверить, что и как было удалено, и воспроизвести процесс.
