# Пояснительная записка: Выбор векторной базы данных (Core #3)

## 1. Введение
В современных RAG-системах (Retrieval-Augmented Generation) выбор хранилища для векторных эмбеддингов является критическим архитектурным решением. Векторная база данных (ВБД) отвечает за эффективный поиск наиболее релевантных фрагментов текста (чанков) по семантическому сходству с вопросом пользователя.

Для проекта «vbudushee» был проведен анализ существующих решений на основе специфики бизнес-требований и технологического стека.

---

## 2. Критерии выбора
При оценке решений использовались следующие ключевые показатели:

1.  **Интеграция с существующим стеком**: Насколько легко база вписывается в текущую архитектуру (Python/Django, PostgreSQL).
2.  **Сложность инфраструктуры**: Требуется ли развертывание и поддержка отдельного сервиса или кластера.
3.  **ACID и надежность**: Гарантии сохранности данных и поддержка транзакций.
4.  **Фильтрация по метаданным**: Возможность эффективно ограничивать поиск в рамках конкретного проекта (`project_id`) или документа.
5.  **Масштабируемость**: Способность обрабатывать миллионы векторов без деградации производительности.
6.  **TCO (Total Cost of Ownership)**: Стоимость лицензий, облачных ресурсов и человеко-часов на поддержку.

## 4. Обоснование итогового выбора: PGVector

Для реализации проекта «vbudushee» выбран **PGVector** (расширение для PostgreSQL). Данный выбор обусловлен следующими факторами:

### 1. Единство данных (Single Source of Truth)
Вся информация — пользователи, проекты, чаты, документы и их векторные представления — хранится в одной базе данных. Это исключает проблему рассинхронизации данных, которая часто возникает при использовании отдельных векторных хранилищ.

### 2. Мощная фильтрация по метаданным
Поиск в RAG почти всегда ограничен контекстом: «найти похожие чанки только в рамках проекта X». В PGVector это обычный `WHERE project_id = ...`. В специализированных ВБД фильтрация по метаданным часто работает медленнее или требует сложной настройки индексов.

### 3. Использование текущей экспертизы
Команда уже работает с PostgreSQL. Не требуется изучение новых протоколов, языков запросов или специфических инструментов мониторинга.

### 4. Транзакционность и надежность
PGVector позволяет в рамках одной транзакции сохранить текст чанка и его вектор. Если произойдет ошибка, данные не сохранятся частично, что гарантирует целостность индекса.

### 5. Экономическая эффективность
Отсутствуют затраты на оплату дополнительных SaaS-решений (как Pinecone) или на выделение ресурсов под тяжелые Java/Go-кластеры (как Milvus).

## 5. Техническая реализация в проекте
В кодовой базе (`core/core/models/data.py`) решение реализовано следующим образом:

- **Модель**: Класс `Chunk` содержит поле `embedding: Mapped[list[float]] = mapped_column(Vector(1024))`.
- **Партиционирование**: Используется хеш-партиционирование по `project_id` (`postgresql_partition_by: "HASH (project_id)"`), что обеспечивает высокую производительность поиска даже при огромном общем количестве данных.
- **Инструментарий**: Библиотека `pgvector-python` для интеграции с SQLAlchemy.

## 6. Резюме
Использование **PGVector** является наиболее прагматичным и эффективным решением для стадии активной разработки и масштабирования проекта, обеспечивая идеальный баланс между производительностью, надежностью и простотой поддержки.
