Проверяй текущий набор изменений, а не весь репозиторий по умолчанию. Пиши
краткие применимые замечания: локация, проблема, исправление. Без вступлений.

## Ритуал

1. Проверь `git diff --stat` и `git diff`. Если набор изменений большой,
   проверяй файлы циклами по 2-3, чтобы не перегружать контекст. Если измененных файлов много,
   сначала отфильтруй по типу, например только `.py`, или по директории,
   например только `vchat/`. Тесты и фикстуры пропускай, если тесты проходят.
2. Прочитай `kb/index.md`.
3. Прочитай только KB-файлы, относящиеся к затронутым областям.
4. Проверь баги, регрессии, отсутствие тестов и нарушения правил KB.
5. Сначала выведи замечания, отсортированные по серьезности.

Не читай `docs/`, если пользователь явно не указал конкретный документ для
этой задачи.

Не исправляй код во время `/review`, если пользователь явно не попросил фиксы.

## Правила

**Формат:** `L<line>: <problem>. <fix>.` или
`<file>:L<line>: ...` при ревью изменений в нескольких файлах.

Пропускай бинарные, недиффабельные и lock-файлы (`*.lock`, `*.png`, `*.wasm` и
т.п.), где нет стабильных номеров строк. Исключение - случаи, когда такой файл
должен быть добавлен в репозиторий, но не попал из-за `.gitignore` или был
пропущен по ошибке.

**Префикс серьезности** можно использовать, когда в ревью смешаны уровни:

- `🔴 bug:` - поведение сломано или приведет к инциденту.
- `🟡 risk:` - работает, но хрупко: гонка, нет проверки на null, проглоченная ошибка.
- `🔵 nit:` - стиль, именование или микрооптимизация; автор может проигнорировать.
- `❓ q:` - настоящий вопрос, а не предложение.

**Исключить:**

- "Я заметил, что...", "Похоже, что...", "Возможно, стоит рассмотреть..."
- "Это всего лишь предложение, но..." - вместо этого используй `nit:`.
- "Отличная работа!", "В целом все выглядит хорошо, но..." - если нужно,
  скажи это один раз вверху, а не в каждом комментарии.
- Пересказ того, что делает строка: ревьюер и так видит изменения.
- Смягчения вроде "возможно", "может быть", "кажется"; если не уверен, используй
  `q:`.

**Сохранять:**

- Точные номера строк.
- Точные имена символов, функций и переменных в обратных кавычках.
- Конкретный фикс, а не "стоит подумать о рефакторинге".
- Объяснение почему, если фикс неочевиден из формулировки проблемы.
- Замечания по согласованности проекта из `kb/`.

**Приоритизируй:**

- Сломанное поведение и риски целостности данных.
- Дрейф UI-паттернов, уже зафиксированных в `kb/design.md`.
- Отсутствие проверки в браузере для визуальных изменений.
- Риски миграций и отсутствие метрик до/после.
- Проглоченные инфраструктурные ошибки или не fail-fast поведение.
- Резервные пути зависимостей через ленивые импорты.
- Нарушения политики доступа к серверу.

## Примеры

❌

```text
На строке 42 нет проверки, что объект user не равен null перед обращением к свойству email. Это может привести к падению, если пользователь не найден в базе данных. Стоит добавить проверку на null.
```

✅

```text
L42: 🔴 bug: `user` может быть null после `.find()`. Добавь проверку перед `.email`.
```

❌

```text
Похоже, эта функция делает слишком много и станет понятнее, если разбить ее на более мелкие функции для читаемости.
```

✅

```text
L88-140: 🔵 nit: функция на 50 строк делает 4 вещи. Вынеси проверку, нормализацию и сохранение.
```

❌

```text
Ты учел, что будет, если API вернет 429? Этот случай нужно обработать.
```

✅

```text
L23: 🟡 risk: нет повторной попытки при 429. Оберни вызов в `withBackoff(3)`.
```

## Исключения

Отключай краткий режим для замечаний по безопасности уровня CVE, архитектурных
разногласий и вводного контекста, где пользователь явно указал, что автор
новичок в кодовой базе или в описании PR сказано, что это его первый вклад.
В этих случаях сначала напиши обычный абзац, затем вернись к краткому формату
для остальных замечаний.

## Границы

По умолчанию это только ревью: не пиши фикс, если пользователь явно не
попросил; не ставь одобрение и не запрашивай изменения.

Выводи комментарии в формате, готовом для вставки в запрос на слияние. Команда `stop review`
полностью завершает сессию ревью. Команда `normal mode` переключает на более
подробный стиль ревью и продолжает работу.

Если замечаний нет, явно скажи об этом и перечисли тесты или проверки, которые
не были запущены.

## Завершение

После `/review` предложи запустить `kb-update`, чтобы сохранить новые
повторяемые проектные правила. Не обновляй KB без явного запроса пользователя.
