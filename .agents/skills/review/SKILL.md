Проверяй текущий набор изменений, а не весь репозиторий по умолчанию. Пиши
краткие, применимые замечания. Локация, проблема, фикс. Без вступлений.

## Project Ritual

1. Проверь `git diff --stat` и `git diff`.
2. Прочитай `kb/index.md`.
3. Прочитай только KB-файлы, относящиеся к затронутым областям.
4. Проверь баги, регрессии, отсутствие тестов и нарушения правил KB.
5. Сначала выведи замечания, отсортированные по серьёзности.

Не читай `docs/`, если пользователь явно не указал конкретный документ для этой задачи.
Не исправляй код во время `/review`, если пользователь явно не попросил фиксы.

## Rules

**Формат:** `L<line>: <problem>. <fix>.` — или `<file>:L<line>: ...` при ревью diff в нескольких файлах.

Пропускай все бинарные/недиффабельные и lock-файлы (`*.lock`, `*.png`, `*.wasm` и т.п.), где нет стабильных номеров строк. Кроме тех случаев когда подразумевается что этот файл должен быть добавлен в репозиторий, но не попал из-за .gitignore или был пропущен по ошибке.

**Префикс серьёзности (опционально, когда уровни смешаны):**

- `🔴 bug:` — поведение сломано, приведёт к инциденту
- `🟡 risk:` — работает, но хрупко (race, нет null-check, проглоченная ошибка)
- `🔵 nit:` — стиль, именование, микрооптимизация. Автор может проигнорировать
- `❓ q:` — настоящий вопрос, а не предложение

**Исключить:**

- "Я заметил, что...", "Похоже, что...", "Возможно, стоит рассмотреть..."
- "Это всего лишь предложение, но..." — вместо этого используй `nit:`
- "Отличная работа!", "В целом всё выглядит хорошо, но..." — скажи это один раз вверху, не в каждом комментарии
- Пересказ того, что делает строка — ревьюер и так видит diff
- Смягчения ("perhaps", "maybe", "I think") — если не уверен, используй `q:`

**Сохранять:**

- Точные номера строк
- Точные имена символов/функций/переменных в обратных кавычках
- Конкретный фикс, а не "consider refactoring this"
- Объяснение _почему_, если фикс неочевиден из формулировки проблемы
- Замечания по согласованности проекта из `kb/`

**Приоритизируй:**

- Сломанное поведение и риски целостности данных
- Дрейф UI-паттернов, уже зафиксированных в `kb/design.md`
- Отсутствие проверки в браузере для визуальных изменений
- Риски миграций и отсутствие метрик до/после
- Проглоченные инфраструктурные ошибки или не fail-fast поведение
- Fallback-и зависимостей через ленивые импорты
- Нарушения политики доступа к серверу

## Examples

❌ `На строке 42 нет проверки, что объект user не равен null перед обращением к свойству email. Это может привести к падению, если пользователь не найден в базе данных. Стоит добавить проверку на null.`
✅ `L42: 🔴 bug: user может быть null после .find(). Добавь проверку перед .email.`
❌ `Похоже, эта функция делает слишком много и станет понятнее, если разбить её на более мелкие функции для читаемости.`
❌ `Похоже, эта функция делает слишком много и станет понятнее, если разбить её на более мелкие функции.`
✅ `L88-140: 🔵 nit: функция на 50 строк делает 4 вещи. Вынеси validate/normalize/persist.`
❌ `Ты учёл, что будет, если API вернёт 429? Этот случай нужно обработать.`
❌ `Что произойдёт, если API вернёт 429? Этот случай нужно обработать.`
✅ `L23: 🟡 risk: нет ретраев при 429. Оберни в withBackoff(3).`

## Авто-ясность

Отключай краткий режим для: замечаний по безопасности (баги уровня CVE требуют полного объяснения + ссылки), архитектурных разногласий (нужна аргументация, а не одна строка) и контекстов онбординга, где пользователь явно указал, что автор новичок в кодовой базе или в описании PR сказано, что это его первый вклад. В этих случаях сначала напиши обычный абзац, затем вернись к краткому формату для остальных замечаний.

## Границы

По умолчанию только ревью — не пишет код фикса, если пользователь явно не попросил; не ставит approve/request-changes.
Выводи комментарии в формате, готовом для вставки в PR. "stop review":
полностью завершить сессию ревью. "normal mode":
переключиться на подробный стиль ревью и продолжить.

Если замечаний нет, явно скажи об этом и перечисли тесты или проверки, которые
не были запущены.
