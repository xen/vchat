### Пояснительная записка: Выбор векторной базы данных

**Проект:** Сервис «ИИ-агент-чат-бот» для АС «ВБУДУЩЕЕ»
**Этап:** Проектирование и согласование архитектуры

---

### 1. Введение
В основе работы современного ИИ-агента лежит технология **RAG (Retrieval-Augmented Generation)**. Для её реализации критически важно наличие хранилища, способного выполнять семантический поиск по векторным представлениям (эмбеддингам) текстовых документов.

Настоящая записка содержит обоснование выбора векторной базы данных (ВБД) для АС «ВБУДУЩЕЕ», исходя из требований к производительности (1000+ сессий), безопасности (SSDLC) и необходимости размещения на серверах Фонда.

---

### 2. Критерии выбора ВБД
Для обеспечения соответствия ТЗ, выбор осуществлялся по следующим критериям:
- **Локальное размещение (On-premise):** Возможность развертывания в закрытом контуре на серверах Фонда. Использование внешних SaaS-решений (Pinecone и др.) исключено согласно требованиям безопасности.
- **Производительность поиска:** Способность обеспечивать время ответа менее 20 секунд при нагрузке в 1000+ одновременных сессий.
- **Гибридная фильтрация:** Возможность мгновенного ограничения поиска по метаданным (например, поиск только в конкретном PDF-файле или категории «паспорта материалов»).
- **Надежность и ACID:** Гарантия сохранности данных, транзакционность и поддержка резервного копирования штатными средствами.
- **Соответствие стеку:** Полная совместимость с языком Python и контейнеризацией Docker/Kubernetes.

---

### 3. Сравнение архитектурных подходов

| Критерий | PostgreSQL + PGVector | Специализированные ВБД (Milvus/Weaviate) | Embedded решения (Chroma/LanceDB) |
| :--- | :--- | :--- | :--- |
| **Размещение** | Внутри инфраструктуры Фонда | Требует отдельного кластера | Внутри контейнера приложения |
| **Сложность поддержки** | Низкая (стандартная СУБД) | Высокая (новые узлы, Java/Go-стек) | Низкая |
| **Фильтрация метаданных** | Максимальная (через SQL Join/Where) | Ограниченная (собственные индексы) | Средняя |
| **Безопасность** | Соответствует стандартам Фонда | Требует отдельного аудита безопасности | Зависит от приложения |
| **Масштабируемость** | Вертикальная + Партиционирование | Высокая горизонтальная | Ограничена |

### 4. Обоснование итогового выбора: PGVector (PostgreSQL)
Для реализации АС «ВБУДУЩЕЕ» в качестве целевого решения выбран **PGVector**. Данный выбор является фундаментально обоснованным по следующим причинам:

#### 4.1. Единый контур безопасности и данных
Использование расширения `pgvector` позволяет хранить бизнес-данные (пользователи, логи сессий) и векторные данные в одной базе. Это критично для соблюдения требований информационной безопасности:
- Упрощается аудит доступа к данным.
- Исключается риск рассинхронизации между текстом документа и его вектором.
- Механизмы идентификации и аутентификации пользователей применяются к БД целиком.

#### 4.2. Эффективная работа с «Паспортами материалов»
ТЗ требует учета метаданных документов (категоризация, местонахождение). PostgreSQL позволяет выполнять сложные SQL-запросы, объединяя семантический поиск с жесткими фильтрами по метаданным в одном запросе. Это гарантирует, что ИИ-агент не выйдет за рамки разрешенного контекста.

#### 4.3. Масштабируемость под нагрузку 1000+ сессий
PGVector поддерживает индекс **HNSW** (Hierarchical Navigable Small World), который обеспечивает высокую скорость поиска на больших объемах данных. В сочетании с механизмом горизонтального масштабирования контейнеров (согласно ТЗ), решение полностью покрывает требования по производительности.

#### 4.4. Технологический суверенитет и поддержка
PostgreSQL является проверенным Open Source решением, широко применяемым в государственных и финансовых структурах РФ. Это гарантирует отсутствие рисков, связанных с санкционными ограничениями или внезапным прекращением поддержки проприетарных технологий.

---

### 5. План технической реализации
В рамках разработки серверной части (Этап 2) планируется следующая конфигурация:
- **Схема данных:** Создание таблицы фрагментов (`chunks`) с типом данных `vector(1024)` для хранения эмбеддингов от GigaChat.
- **Индексация:** Использование индексов **HNSW** для ускорения поиска top-k по косинусному сходству (cosine distance).
- **Партиционирование:** Разделение данных по идентификаторам разделов портала для оптимизации нагрузки.
- **Мониторинг:** Экспорт метрик производительности БД в Prometheus для контроля SLO.

---

### 6. Резюме
Выбор **PGVector** позволяет Заказчику получить надежное, производительное и безопасное решение, полностью интегрированное в существующую ИТ-инфраструктуру, без затрат на поддержку дополнительных сложных систем и без рисков утечки данных во внешние сети.
