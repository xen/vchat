### Пояснительная записка: Выбор векторной базы данных

**Проект:** Сервис «ИИ-агент-чат-бот» для АС «ВБУДУЩЕЕ»
**Этап:** Проектирование и согласование архитектуры

## 1. Введение

В основе современного ИИ-агента лежит технология **RAG (Retrieval-Augmented Generation)** — динамическое дополнение контекста языковой модели релевантными фрагментами документов, найденными по смысловой близости. Для реализации данной технологии критически важно наличие хранилища, способного выполнять быстрый **семантический поиск по векторным представлениям (эмбеддингам)** текстовых документов.

Настоящая записка содержит развёрнутое обоснование выбора векторной базы данных (ВБД) для АС «ВБУДУЩЕЕ». При выборе учитывались требования к производительности (1000+ одновременных сессий), безопасности (SSDLC), необходимость размещения на серверах Фонда, а также условия российского рынка программного обеспечения.

> **Итоговый выбор:** PGVector (расширение PostgreSQL). Обоснование приведено в разделах 4–6 настоящей записки.

## 2. Критерии выбора векторной базы данных

Выбор ВБД осуществлялся на основании следующих ключевых критериев, вытекающих из требований технического задания и условий эксплуатации:

- **On-premise размещение** — обязательное развертывание в закрытом контуре на серверах Фонда. Использование внешних облачных SaaS-решений (Pinecone, Weaviate Cloud, Zilliz Cloud) исключено требованиями информационной безопасности.
- **Производительность и время отклика** — обеспечение ответа на запрос менее 20 секунд при нагрузке в 1000+ одновременных пользовательских сессий.
- **Гибридная фильтрация** — возможность мгновенного ограничения области поиска по метаданным документов (фильтрация по конкретному PDF-файлу, категории «Паспорта материалов», разделу портала).
- **Надёжность и ACID** — гарантии сохранности данных, транзакционность, поддержка резервного копирования штатными средствами.
- **Экономическая эффективность** — минимальная совокупная стоимость владения (ТСО) с учётом лицензирования, развертывания и эксплуатации.
- **Соответствие российскому ИТ-контуру** — поддержка провайдеров российского рынка, наличие документации на русском языке.
- **Технологический стек** — полная совместимость с Python и контейнеризацией Docker/Kubernetes.

### 3.1. Специализированные векторные СУБД (Milvus, Weaviate)

Milvus и Weaviate являются полнофункциональными специализированными системами для работы с векторными данными. Они обеспечивают высокую горизонтальную масштабируемость, однако несут значительные накладные расходы:

- Требуют развертывания отдельного кластера (минимум 2–4 узла для Milvus с зависимостью от etcd и объектного хранилища).
- Технологический стек (Go, Java) выходит за пределы компетенций Python-команды.
- Фильтрация по метаданным реализована через собственные API, что ограничивает гибкость при сложных бизнес-сценариях.
- Официальная поддержка российскими хостинг-провайдерами отсутствует или существенно ограничена.
- Безопасность требует отдельного аудита ввиду отсутствия истории применения в аналогичных отечественных проектах.

### 3.2. Встраиваемые решения (Chroma, LanceDB)

Chroma и LanceDB представляют собой лёгкие библиотеки, встраиваемые непосредственно в контейнер приложения. Несмотря на простоту начальной настройки, они имеют существенные ограничения для продуктовой эксплуатации:

- Ограниченная масштабируемость при объёмах данных, характерных для нагруженных систем.
- Отсутствие ACID-транзакций: риск рассинхронизации данных при сбоях и параллельной записи.
- Слабый механизм безопасности: разграничение доступа реализуется исключительно на уровне приложения.
- Незрелость для production: оба проекта имеют относительно короткую историю эксплуатации в нагруженных системах.

## 4. Обоснование выбора PGVector (PostgreSQL)

По результатам сравнительного анализа в качестве целевого решения выбран **pgvector** — расширение для PostgreSQL, разработанное специально для хранения и поиска по векторным эмбеддингам. Данный выбор является фундаментально обоснованным по совокупности технических, экономических и регуляторных факторов.

### 4.1. Единый контур безопасности и данных

Расширение pgvector позволяет хранить бизнес-данные (пользователи, сессии, логи) и векторные данные в единой базе данных PostgreSQL:

- Упрощается аудит доступа: все операции протоколируются единым механизмом PostgreSQL.
- Исключается риск рассинхронизации между текстом документа и его вектором — текст и эмбеддинг хранятся в одной транзакции.
- Механизмы аутентификации и авторизации (RBAC, row-level security) применяются ко всей базе данных единообразно.
- Сокращается поверхность атаки: отсутствует необходимость открывать порты для внешней векторной СУБД.

### 4.2. Производительность при нагрузке 1000+ сессий

Начиная с версии 0.5.0, pgvector поддерживает индекс **HNSW (Hierarchical Navigable Small World)** — широко признанный алгоритм приближённого поиска ближайших соседей (ANN). Он обеспечивает:

- Субмиллисекундное время поиска по миллионам векторов при высоком параллелизме.
- Настраиваемый баланс между точностью поиска (recall) и скоростью (параметры `m` и `ef_construction`).
- Эффективный поиск с предварительной фильтрацией по метаданным через стандартные SQL WHERE-условия.

В сочетании с горизонтальным масштабированием контейнеров приложения (как предусмотрено ТЗ) решение полностью покрывает требования по производительности.

### 4.3. Эффективная работа с «Паспортами материалов» и метаданными

PostgreSQL позволяет объединять семантический поиск с точной SQL-фильтрацией в рамках единого запроса:

```sql
SELECT chunk_text, 1 - (embedding <=> $1) AS score
FROM chunks
WHERE category = 'passport' AND section_id = $2
ORDER BY embedding <=> $1
LIMIT 5;
```

Такой подход гарантирует, что ИИ-агент не выйдет за пределы разрешённого контекста документов.

### 4.4. Технологический суверенитет

PostgreSQL занимает устойчивое место в российском ИТ-ландшафте:

- Является Open Source-проектом без иностранных правообладателей на ключевые компоненты, что исключает риски, связанные с санкционными ограничениями или отзывом лицензий.
- Широко применяется в государственных, финансовых и промышленных структурах РФ, что подтверждается публичными кейсами и отраслевыми исследованиями.

## 8. План технической реализации

### 8.1. Схема данных

```sql
CREATE EXTENSION IF NOT EXISTS vector;

CREATE TABLE chunks (
    id          BIGSERIAL PRIMARY KEY,
    doc_id      UUID NOT NULL REFERENCES documents(id),
    section_id  INTEGER,
    category    VARCHAR(64),
    chunk_text  TEXT NOT NULL,
    embedding   vector(1024),
    created_at  TIMESTAMPTZ DEFAULT NOW()
);

-- HNSW-индекс для косинусного поиска
CREATE INDEX ON chunks USING hnsw (embedding vector_cosine_ops)
    WITH (m = 16, ef_construction = 64);

-- Индекс по метаданным для гибридной фильтрации
CREATE INDEX ON chunks (category, section_id);
```

### 8.2. Параметры индекса HNSW

| Параметр          | Значение            | Описание                                                                    |
| :---------------- | :------------------ | :-------------------------------------------------------------------------- |
| `m`               | 16                  | Количество связей на узел графа; оптимально для объёмов до ~10 млн векторов |
| `ef_construction` | 64                  | Ширина луча при построении индекса                                          |
| `ef_search`       | 40–100              | Ширина луча при поиске; увеличить для повышения recall                      |
| Метрика           | `vector_cosine_ops` | Косинусное расстояние — оптимально для текстовых эмбеддингов                |

### 8.3. Мониторинг и SLO

- Экспорт метрик производительности БД в Prometheus через `postgres_exporter`.
- **SLO:** p95 времени векторного поиска (top-5) — не более 500 мс при 1000 одновременных запросов.
- Алерты на деградацию индекса, рост очереди autovacuum, превышение connection pool.
