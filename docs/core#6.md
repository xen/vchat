# План наблюдаемости (Core #6) 

## 1. Введение
Наблюдаемость (Observability) системы «vbudushee» необходима для обеспечения стабильной работы RAG-конвейера, быстрого обнаружения сбоев в индексации данных и контроля качества ответов ИИ. План базируется на трех столпах: метрики, логи и алерты.

---

## 2. Ключевые метрики (Metrics)

Метрики разделены на системные (инфраструктурные) и прикладные (бизнес-логика RAG).

### 2.1. Web API (Django/aiohttp) — Golden Signals
- **Latency**: Время обработки HTTP-запросов и WebSocket-сообщений (p50, p95, p99).
- **Traffic**: Количество запросов в секунду (RPS) по эндпоинтам.
- **Errors**: Процент ответов 4xx и 5xx. Особое внимание на ошибки CSRF и Auth.
- **Saturation**: Загрузка CPU/RAM инстансов приложения и количество активных соединений WebSocket.

### 2.2. RAG & LLM (Прикладные метрики)
- **LLM Latency**: Время генерации ответа моделью (TTFT — Time To First Token и полное время).
- **Token Usage**: Потребление токенов в разрезе проектов и провайдеров (OpenAI/Anthropic/Local).
- **Retrieval Quality**: Hit Rate (находится ли релевантный контекст в топ-k результатах).
- **Vector Search Latency**: Время выполнения Similarity Search в PGVector.

### 2.3. Background Tasks (Celery & Crawlers)
- **Queue Depth**: Количество задач в очередях `crawler` и `embeddings`.
- **Task Duration**: Время выполнения индексации документа/сайта.
- **Failure Rate**: Процент упавших задач (Crawler Failures, Embedding Errors).
- **Resource Usage**: Потребление памяти во время обработки тяжелых PDF/Docx.

---

## 3. Логирование (Logging)

### 3.1. Уровни и форматы
- **Формат**: Использование структурированного логирования (JSON) в продакшн-среде для интеграции с ELK/Grafana Loki.
- **Уровни**:
    - `INFO`: Жизненный цикл запросов, успешная индексация источников.
    - `WARNING`: Ошибки доступа, превышение лимитов (Rate Limiting), таймауты LLM.
    - `ERROR`: Исключения в коде, сбои БД, неудачные попытки вызвать API LLM.

### 3.2. Ключевые события для отслеживания
- `auth_middleware`: Ошибки аутентификации и инвалидация сессий.
- `on_upload_done`: Статус загрузки файлов через TUS.
- `crawl_source_task`: Выходные данные (stdout/stderr) подпроцессов краулеров.
- `similarity_search`: Логирование параметров поиска при низком пороге схожести.

---

## 4. Алертинг (Alerting)

### 4.1. Критические алерты (Immediate action)
- **Service Down**: API или WebSocket недоступны.
- **DB Connection Fail**: Ошибки подключения к PostgreSQL или Redis.
- **High Error Rate**: >5% ошибок 5xx в течение 5 минут.
- **LLM Provider Outage**: Массовые ошибки от OpenAI/Anthropic.

### 4.2. Предупреждающие алерты (Investigation needed)
- **Stuck Crawling**: Очередь задач не уменьшается в течение часа.
- **Budget Spike**: Резкий рост потребления токенов конкретным проектом.
- **Slow Responses**: Среднее время ответа чата > 10 секунд.

---

## 5. Инструментарий (Stack)

Для реализации плана рекомендуется следующий стек:
1. **Prometheus**: Сбор метрик приложения и экспортеров (Postgres Exporter, Redis Exporter).
2. **Grafana**: Визуализация дашбордов (RAG Health, System Overview).
3. **Sentry**: Отслеживание исключений (уже интегрировано в `error_middleware`).
4. **Grafana Loki / ELK**: Централизованный сбор и поиск по логам.

---

## 6. Резюме
Внедрение данного плана позволит не только быстро реагировать на инциденты, но и понимать экономическую эффективность системы через контроль потребления ресурсов LLM и производительность фоновых задач.
