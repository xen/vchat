## 4. Характеристика документов

### 4.1 Документ 01. Архитектурная схема и пояснительная записка

Документ задает базовую архитектурную рамку сервиса. В нем описано назначение
чат-бота, интегрированного в портал АС «ВБУДУЩЕЕ», и закреплено, что сервис
предназначен для круглосуточной поддержки пользователей с ответами на основе
материалов Заказчика и обязательной привязкой к источникам.

**Структура документа:**

- цели сервиса: автоматизация ответов по материалам Заказчика, бесшовная
  интеграция с порталом, поддержка высокой нагрузки, выполнение требований
  безопасности;
- C4 Model, уровень System Context: пользователь, портал, администратор,
  Active Directory, внешние источники, GigaChat API и сервис VChat;
- C4 Model, уровень Containers: nginx, backend, Celery Worker, Redis / Valkey,
  PostgreSQL + pgvector, статические ресурсы и шаблоны;
- сценарий пользовательского запроса: от открытия виджета и передачи вопроса
  до поиска контекста, обращения к ИИ-провайдеру, возврата ответа и сохранения
  истории;
- сценарий индексации: административный запуск или событие от внешнего
  источника, постановка задачи в очередь, обработка worker-процессом,
  chunking, embeddings и запись в хранилище;
- технологический стек: Python/aiohttp, Celery, PostgreSQL + pgvector, Redis /
  Valkey, nginx, контейнерное развертывание, LDAP/AD, метрики и JSON-логи.

**Краткое содержание:** архитектурная записка задает системную основу проекта.
Она показывает границы сервиса, его компоненты, внешние зависимости и основные
потоки данных. Этот документ является опорным для всех последующих материалов:
API, индексация, безопасность, сеть, наблюдаемость и приемка ссылаются на те
же компоненты и сценарии.

### 4.2 Документ 02. OpenAPI-спецификация

Документ описывает публичные API-методы, необходимые для синхронизации и
индексации документов по URL, а также содержит справку по подключению виджета
на сайт.

**Структура документа:**

- назначение API обновления материалов;
- описание endpoint `/api/update` для передачи URL материала на обработку;
- модель защищенного вызова через `client_id` и HMAC-SHA256 подпись;
- параметры запроса, включая целевой URL и подпись;
- ответы API и примеры использования;
- пример клиентского вызова для индексации документа;
- базовый код встраивания виджета в страницу;
- рекомендации по размещению контейнера виджета и подключению клиентского
  скрипта.

**Краткое содержание:** спецификация фиксирует внешний контракт между сервисом
и системами, которые инициируют обновление материалов. Документ также связывает
backend API с пользовательским каналом работы через виджет: внешний контур
может обновлять базу знаний, а пользовательский интерфейс использует
подготовленный виджет для обращения к чат-боту.

### 4.3 Документ 03. Пояснительная записка с выбором векторной БД

Документ обосновывает технологический выбор хранилища для векторного поиска,
необходимого в RAG-архитектуре.

**Структура документа:**

- вводное описание роли RAG и embeddings в работе ИИ-агента;
- критерии выбора векторной базы данных: производительность, on-premise
  размещение, контейнеризация, стоимость владения, поддержка российского
  инфраструктурного контура, зрелость и надежность;
- сравнительный анализ PostgreSQL + pgvector, Milvus / Weaviate, Chroma /
  LanceDB;
- сравнение по ACID, SQL-фильтрации, HNSW-индексам, эксплуатации, TCO,
  зрелости и удобству промышленного сопровождения;
- итоговое обоснование выбора PostgreSQL + pgvector.

**Краткое содержание:** выбор PostgreSQL + pgvector обоснован как наиболее
практичный для проекта: одно хранилище покрывает данные, chunks, embeddings,
metadata и историю диалогов. Это снижает число инфраструктурных компонентов,
упрощает резервное копирование и контроль доступа, а также позволяет совмещать
семантический поиск с обычными SQL-фильтрами.

### 4.4 Документ 04. Индексация сайтов: регламент и операционная модель

Документ описывает операционный регламент индексации сайтов: как источник
подключается, проверяется, обходится, очищается и доводится до состояния,
пригодного для поиска.

**Структура документа:**

- прикладные определения: источник, страница, документ, chunk, embedding,
  обход и индексация;
- цели индексации: поддерживать базу знаний, не перегружать внешние сайты,
  исключать технические и мусорные страницы, передавать в поиск только
  проверенные фрагменты;
- роли и зоны ответственности: администратор источников, система обхода,
  система подготовки документов, система индексирования и операционный
  контроль;
- основные сущности: источник, sitemap, страница, связь страниц, запуск
  обхода, chunk, шингл;
- жизненный цикл источника: активный режим, пауза, блокировка, ручной режим;
- предварительные проверки: DNS, robots.txt, главная страница, server errors,
  редиректы;
- регламент обнаружения URL через стартовую страницу, sitemap и ссылки;
- правила работы с sitemap, включая `lastmod`, ETag, sitemap index и ручное
  добавление;
- критерии качества документа и подходы к повторной обработке.

**Краткое содержание:** регламент описывает технический краулер, обеспечивающий
управляемый процесс наполнения базы знаний. Документ важен для
эксплуатации, потому что определяет, почему одни страницы попадают в поиск, а
другие исключаются, как контролируется нагрузка на сайты и как обеспечивается
предсказуемое обновление контента.

### 4.5 Документ 04.1. Цитирование источников в чатах

Документ описывает пользовательскую и системную модель цитирования источников
в ответах чат-бота.

**Структура документа:**

- назначение цитирования: показать основу ответа, снизить риск
  неподтвержденных утверждений и дать пользователю путь к первичному
  документу или странице;
- ключевые понятия: вопрос, контекст, фрагмент, номер цитирования, источник,
  покрытие, пользовательская ссылка;
- общий принцип: цитирование строится до генерации ответа, а не добавляется
  после него;
- поиск релевантных фрагментов через семантический и полнотекстовый поиск;
- профили запроса: обычный ответ, запрос на источник или цитату, табличный
  запрос, перечисление;
- отбор и ранжирование фрагментов, дедупликация и ограничение объема
  контекста;
- присвоение номеров цитирования выбранным фрагментам;
- правила передачи контекста модели и запрет на выдуманные ссылки;
- пользовательское отображение: номерные метки, кликабельные источники и
  панель источников;
- сохранение использованных источников и fragments в истории чата;
- контроль качества цитирования и защитные проверки.

**Краткое содержание:** регламент цитирования закрепляет проверяемость ответа
как отдельное качество сервиса. Он связывает RAG-поиск, поведение модели и
интерфейс виджета в единый процесс: пользователь видит не только текст ответа,
но и связь ответа с исходными материалами.

### 4.6 Документ 05. Политики безопасности виджета и сервиса

Документ описывает защитные меры для клиентского виджета, серверной части,
данных, LLM-слоя и административного интерфейса.

**Структура документа:**

- подход Defense in Depth и SSDLC;
- защита виджета от XSS и инъекций;
- безопасная интеграция через JS-сниппет;
- управление сессиями и изоляция пользовательского взаимодействия;
- server-side защита от SQL-инъекций и несанкционированного доступа;
- защита от утечек и работа с персональными данными;
- LLM Guardrails: prompt injection, фильтрация ввода, контроль вывода,
  блокировка небезопасных данных;
- URL filter и ограничение ссылок доменами Фонда;
- мониторинг и аудит безопасности;
- реагирование на инциденты;
- проверки безопасности в CI/CD;
- административный доступ и маскирование чувствительной информации в
  интерфейсе.

**Краткое содержание:** политики безопасности покрывают основные поверхности
риска: публичный виджет, внешний API, backend, базу данных, LLM-провайдера и
административный контур. Документ фиксирует, что безопасность сервиса строится
не на одной проверке, а на сочетании изоляции, подписей, фильтрации,
ограничения доступа, журналирования и процедур реагирования.

### 4.6.1 Документ 05.1. OWASP ASVS L1+L2 чеклист

Документ закрывает отдельное договорное требование по OWASP ASVS LVL1+LVL2 для
web-приложения и оформлен как проверочный реестр по OWASP ASVS 5.0.0.

**Структура документа:**

- область проверки: web-приложение, фоновые задачи, deploy-артефакты,
  security reports и эксплуатационная документация репозитория;
- легенда статусов: `Covered`, `Partial`, `Missing`, `N/A`,
  `Accepted external`, `TBD`;
- индекс доказательств: проверка безопасности artifacts, отчеты Codex Security,
  `bin/проверка безопасности.sh`, deploy/Kubernetes материалы, `docs/manual.md` и
  регрессионные тесты;
- итоговая сводка по 253 требованиям ASVS L1+L2;
- отдельный список незакрытых или требующих принятия пунктов;
- deployment recommendations для инфраструктурных зон Заказчика: AD/LDAP/IdP,
  MFA, TLS/Ingress, SIEM, Kubernetes, registry и антивирусный контур;
- отдельный пакет `docs/asvs_external_evidence_package.md` с deployment
  recommendations и пояснением границ ответственности для пунктов,
  классифицированных как `N/A` вне область кода приложения;
- проверочная команда `venv/bin/python bin/asvs-checklist-verify.py`, которая
  подтверждает синхронизацию рабочего чеклиста, финального отчета и пакета
  внешних evidence;
- машиночитаемые manifest `docs/asvs_external_evidence_manifest.json` и
  папка `docs/asvs_external_evidence/` на случай будущего расширения scope до
  runtime/customer infrastructure evidence;
- generated status `docs/asvs_external_evidence_status.md`, который фиксирует,
  что в текущем область кода приложения нет блокирующих external evidence rows;
- строгий финальный режим `venv/bin/python bin/asvs-checklist-verify.py --require-external-evidence`,
  который сейчас проходит, потому что в текущем область кода приложения нет
  строк со статусом `Accepted external`;
- основной чеклист по разделам ASVS V1-V17.

**Описание пунктов чеклиста:** каждая строка чеклиста содержит не только номер
ASVS, но и понятное описание сути проверки. Для каждого пункта указано, что
именно проверяется: например, канонизация и output escaping, защита от SQL/OS/
LDAP/regex/template/SSRF-инъекций, безопасная обработка файлов, парольные
правила, управление сессиями, CORS/CSRF/CSP/HSTS, WebSocket origin checks,
OAuth/OIDC неприменимость, криптография, TLS, секреты, конфигурация, защита
данных, secure coding, журналирование, обработка ошибок и WebRTC
неприменимость.

**Краткое содержание:** ASVS-чеклист является финальным контрольным документом
по пункту 62 листа согласования. Он позволяет комиссии идти по каждому
требованию ASVS L1+L2 и видеть пять вещей в одной строке: идентификатор
требования, уровень ASVS, человеческое описание проверки, текущий статус
покрытия и конкретное evidence в коде, тестах, конфигурации, проверка безопасности
artifacts или внешнем инфраструктурном контуре.

**Содержание пунктов ASVS L1+L2:** ниже перенесены понятные описания каждого пункта из рабочего чеклиста вместе с пояснениями, командами проверки и ссылками на evidence. Это приложение нужно для чтения отчета без постоянного перехода в отдельный файл: комиссия видит не только номер пункта, но и смысл проверки, статус и основание вывода. Источником синхронизации остается `docs/asvs_l1_l2_checklist.md`.

### 4.7 Документ 06. План наблюдаемости

Документ описывает метрики, логи и контрольные сигналы, необходимые для
эксплуатационного наблюдения за сервисом.

**Структура документа:**

- назначение наблюдаемости для RAG-конвейера, качества ответов и безопасности;
- метрики мониторинга;
- структурированное JSON-логирование;
- запрет попадания фактических пользовательских данных в метрики и логи;
- связь метрик с эксплуатационными алертами.

**Краткое содержание:** план наблюдаемости задает основу для контроля
работоспособности сервиса после развертывания. Он покрывает не только
технические Golden Signals, но и специфические для RAG параметры: качество
контекста, расход токенов, работу guardrails, состояние индексации и очередей.

### 4.8 Документ 07. Календарный план и критерии приемки

Документ определяет график реализации сервиса и условия, при которых работы
считаются выполненными в полном объеме.

**Краткое содержание:** календарный план связывает проектную документацию с
практической реализацией и приемкой. Он показывает, какие deliverables должны
быть получены на каждом этапе, и задает измеримые критерии результата:
интеграция, индексация, источники, производительность, безопасность,
наблюдаемость и эксплуатационная готовность.

### 4.9 Документ 08. Схема сетевого взаимодействия

Документ описывает сетевую схему сервиса в инфраструктурной модели Cloud.ru,
включая внутренние коммуникации между компонентами и внешние интеграции.

**Структура документа:**

- назначение документа для согласования логической сетевой схемы и принципов
  сегментации;
- общая структура сети на базе Kubernetes;
- разделение на Frontend VPC и Backend VPC;
- таблица сетевых потоков;
- сетевые принципы: минимальные привилегии, TLS 1.2+, изоляция,
  аутентификация исходящих вызовов, управление секретами, журналирование
  сетевых событий.

**Краткое содержание:** схема сетевого взаимодействия дополняет архитектуру
прикладного уровня инфраструктурной моделью. Документ показывает, какие
каналы нужны сервису, какие зоны должны быть изолированы, где проходят
публичные и внутренние потоки, и какие правила потребуются для настройки
firewall, security groups, ingress и мониторинга.

### 4.10 Документ 09. Стратегия индексации сайтов проекта

Документ описывает стратегию индексации обширного набора сайтов проекта с
учетом технологического стека и типа контента.

**Структура документа:**

- выделение основной группы контентных ресурсов, включая сайт Фонда,
  образовательные порталы, каталоги, навигаторы, конкурсы, грантовые и
  диагностические платформы;

**Краткое содержание:** стратегия индексации сайтов переводит общий регламент
индексации в практическую модель для реального набора ресурсов АС
«ВБУДУЩЕЕ». Она показывает, что разные сайты нельзя обрабатывать одинаково:
метод обхода и глубина извлечения зависят от платформы, структуры страниц,
качества sitemap и типа пользовательского контента.
